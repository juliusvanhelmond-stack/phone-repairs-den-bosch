# Phone Repairs — redesign (JUNE Studio)

Next.js 16 (App Router, Cache Components) + TypeScript + Tailwind v4 site for Phone Repairs Den Bosch.
Phase 1 demo; the live site www.phonerepairs.nl is never modified. Read AGENTS.md: this Next.js
version differs from older training data — check `node_modules/next/dist/docs/` before using an API.

## Commands
- `npm run dev` / `npm run build` (runs `validate:data` first) / `npm start`
- `npm run check` — typecheck, lint, data validation, parser test
- `npm run test:smoke` — Playwright E2E + axe against a running server (`BASE_URL`, default :3000)
- `npm run screenshots` — full-page screenshots at 375/768/1024/1440 into docs/screenshots
- `npm run migrate` — discover → fetch → parse → analyze → report (see docs/migration-plan.md)
- `npm run import:wordpress -- <export.xml> [--write]` — import the client's WordPress export (dry-run report without `--write`)

## Architecture
- `src/types/content.ts` — zod schemas = the content model (brands, devices, repairs, prices, FAQ, claims, URL inventory).
- CMS (Keystatic, `keystatic.config.ts`, docs/cms.md): pages (`src/content/pages/<id>.json`, one file per kept page; blocks can carry a rate list `prices`), SEO overrides per URL (`src/content/seo/`), the announcement bar (`src/content/announcement.json`), and since 2026-10-21 devices with their price lists (`src/content/toestellen/<slug>.json`, `scripts/content/devices.ts`), blog posts (`src/content/blog/<slug>.mdoc`, Markdoc) and opening hours (`src/content/openingstijden.json`) are edited at /keystatic; `npm run content` merges them into `src/data/generated/` (git-ignored: devices, price lists, blog with rendered HTML, pages, SEO) before dev/build/check. Never edit the generated files. Provenance fields in CMS files use `fields.ignored()` so saves keep them.
- `src/data/*.json` — content. `npm run import:wordpress` (client's WordPress export, WXR, never committed: it holds account e-mails) wrote the device files in `src/content/toestellen/`, `brands.json`, the info pages in `src/content/pages/`, the FAQs and the original URLs in `url-inventory.json`. Since 2026-10-21 the shop edits devices, prices and blog posts in the CMS: don't run the importer with `--write` again (it would overwrite those edits); change the CMS files instead. English for imported text is written by hand in `translations/en.json`.
- Price lists are verbatim rows from the original model pages (`label`, `raw`, `amount`, `status`, `repairId`); `fromPrice` gives the "vanaf" price per repair category, `priceRows` the rows. Devices are ordered by the original menu (`order`); `releaseYear` is optional. Nintendo Switch models come from `/nintendo-switch-reparatie` in the export (brand `nintendo`, category `console`, client request 2026-10-16).
- `src/lib/catalog.ts` — validated data + lookups; the only way components read content.
- `src/lib/site.ts` — contact details, opening hours (CMS file `src/content/openingstijden.json`, by appointment), the terms/privacy PDFs (kept on their original `/wp-content/uploads/…` paths in `public/`) and env flags (`isDemo`, `allowIndexing`).
- Client requests (mail 2026-10-13, 23:21): "altijd op afspraak" everywhere (the importer rewrites "alleen op afspraak" in imported text), brand order iPhone, Samsung, Google, OPPO, OnePlus, Xiaomi, Poco, Redmi, Motorola, Huawei, Honor, Nokia, Sony, Realme, Asus (`BRANDS` in the importer; iPad/MacBook last in mixed lists), no WhatsApp/Bel buttons in the page on mobile (the pinned bar has them).
- Client requests (mail 2026-10-14, 10:39): "binnen 30 minuten" instead of "binnen ongeveer 30 minuten" (also in the importer, which also drops sentences the old site repeats back to back); on mobile the WhatsApp widget never opens by itself but shows a bullet on the bar's WhatsApp button (`WhatsAppNotifyDot`); partner links with the shop's referral code live in `site.partners` (Stellar data recovery form embedded on /data-recovery, Trade-in on the homepage and /pre-owned-toestellen) and must be kept exactly.
- Client layout requests (2026-10-13): a `TopBar` above the sticky header on every page (today's hours, Google/Trustindex badge top right; Kiyoh top left on mobile), Kiyoh fixed bottom left on desktop only, a pinned WhatsApp/Bellen bar on mobile (`MobileActionBar`), "Menu" next to the hamburger, no model counts anywhere, Apple shown as iPhone/iPad/MacBook (`brandLabel`, `brandEntries`) with Simple Icons marks (`brand-marks.ts`, CC0), clickable finder steps, "Meest gekozen" badges and quality links in price rows (from the export).
- Send-in form (`SendInSection` on `/veelgestelde-vragen/reparatie-opsturen`, fields from the shop's Reparatieformulier .doc in `public/wp-content/uploads/2026/09/`): posts to `src/app/api/opsturen/route.ts`, which mails the shop via Resend only when `RESEND_API_KEY`, `FORM_MAIL_TO` and `FORM_MAIL_FROM` are set (`src/lib/mail.ts`, server-side secrets). Otherwise it answers `not-configured` and the form says it was not sent (WhatsApp/e-mail/print fallbacks). Landing sections can carry an original `image` (kept on its `/wp-content/uploads/…` path); price images are shown as images, never retyped.
- Client requests (mails 2026-10-18/20): the finder's last step lets the visitor choose the part option (rows from `/api/prijzen/[device]`, a route handler prerendered per device so the homepage stays light), shows a summary and puts device, repair, option and price in the WhatsApp message, worded as a request (the time is confirmed later). Model search sits above the categories and matches from the start of a word. The hero's main button is "Bekijk jouw reparatieprijs" with WhatsApp beside it; the language switch sits in the top bar left of the theme switch; the logo restarts the homepage when already on it; iPad Pro/Air/mini before 2021 and iPads before 2020 are dropped (`REMOVED_MODELS`); iPhone battery rows link to `/iphone-batterij-vervanging` (kept on its original URL again); the favicon is the current site's own. Mail 2026-10-21: iPhones before the iPhone 7 and the non-existent iPhone 9 / 9 Plus are dropped; "origineel Apple Service pack" links outside battery rows go to `/iphone-onderdelen-kalibreren`; the homepage shows two devices each for iPhone, Samsung, OPPO and Pixel under "Veelgevraagde reparaties"; the location blocks embed the current site's Google Maps card (`site.mapEmbedUrl`).
- Reviews: Google via the client's Trustindex widget (`site.reviews`), Kiyoh via `site.kiyoh`. The Kiyoh score/count are fetched before each build by `npm run reviews:fetch` (needs `KIYOH_FEED_HASH`, a secret) into the git-ignored `src/data/generated/kiyoh.json`; without it the badges show a plain link. Don't fetch reviews at runtime with `"use cache"`: it made client prefetches hang.
- Two languages (`src/lib/i18n.ts`). All pages live under `src/app/[lang]` with Dutch folder names; `src/proxy.ts` rewrites public URLs to them. Dutch keeps the original unprefixed URLs (`/nl/*` 308s to `/*`); English lives under `/en` with translated segments (`/en/repairs`, `/en/repair/screen-replacement`, `/en/faq`, …; landing, brand, device and blog slugs stay Dutch). Unknown URLs get a real 404: the proxy fetches the static `[lang]/niet-gevonden` page and returns it with status 404.
- Code and data always use Dutch paths; `Link` from `@/components/i18n/link` localizes them (never wrap its href in `href()` again). UI strings are co-located as `t("nl", "en")` (`getI18n()` in server components, `useI18n()` in client components). Content translations live in `src/data/translations/en.json` and are applied with the `localize*` helpers in `catalog.ts`; `validate:data` fails when a record has no English entry. `pageMetadata` needs `locale` and sets canonical + hreflang. The language switch is a plain `<a>` (cross-locale prefetch loops the router).
- `src/app/[lang]` routes: `/`, `/reparaties`, `/reparaties/[brand]`, `/reparaties/[brand]/[model]`, `/reparatie/[repair]`, info pages; `sitemap.ts` (both languages with alternates) and `robots.ts` stay at the `src/app` root.
- Pages that keep their original URL live in `src/content/pages/` (area pages, Nintendo Switch, pre-owned, FAQ topics) and render through `src/app/[lang]/[page]` and `src/app/[lang]/veelgestelde-vragen/[topic]` with `LandingTemplate`; blog posts in `src/content/blog/` (CMS) under `/blog-post/[slug]`. Static routes are listed in `src/lib/routes.ts`; `src/proxy.ts` 404s every unknown dynamic path.
- SEO (audit HV Media, 2026-10-13): every published URL of the export ends in one 301/308 on a 200 page (`skipTrailingSlashRedirect`; the proxy strips the WordPress trailing slash and maps unknown old place URLs `/{telefoon|gsm|iphone|…}-reparatie(s)-{plaats}` to that place's page). Area pages get the original text of their own URL from the importer; no old place URL goes to /werkgebied. Titles: `titleFor` in `seo.ts` (suffix " | Phone Repairs", none above 60 characters or when the title already names the shop); old Yoast titles with "bel: 073…" are dropped. The homepage H1 is "Telefoon reparatie Den Bosch".
- Dynamic routes use `generateStaticParams` + `notFound()` and `export const instant = false` (real 404s, fully static pages).
- `src/components/{layout,home,devices,repairs,forms,ui,motion}`; UI primitives follow shadcn/ui conventions on `radix-ui`.
- Device cards, device pages and the finder show one licensed product photo per device type on white (`DevicePhoto`, `src/assets/devices/`, mapping in `devicePhotoKey`); they are examples of the type, never presented as the exact model. Foldables and small list icons use the SVG render (`DeviceArt`). Atmosphere photos (hero, about, process band, CTA) are the shop's own photos of Martijn (sent 2026-10-12) in `src/assets/photos/`, listed in docs/image-credits.md; add new photos there too and never present stock photos as the shop itself.
- `src/components/iphone/` — homepage 3D exploded-view section (React Three Fiber). `parts.ts` is the single source for part offsets, scroll windows, labels and repair links; `model.tsx` swaps the procedural stand-in for a licensed GLB via `NEXT_PUBLIC_IPHONE_MODEL_URL` (spec: docs/3d-model-requirements.md). The WebGL bundle is lazy-loaded; no-WebGL and reduced-motion fallbacks must keep working.
- `scripts/{discovery,migration,validation,lib}` — migration pipeline and QA tooling (run with tsx).

## Content-preservation rules (non-negotiable)
1. Never invent prices, warranty terms, reviews, ratings, opening hours or appointment slots.
2. Every record from the old site keeps its source URL (`sources[]`, `legacyUrls[]`); unknown fields go to `extra`.
3. Prices come only from the shop: first the price lists of the original site (WordPress export, with source URL and page date), since 2026-10-21 the shop's own edits in the CMS. Shown as written; rows without an amount stay "Op aanvraag". Never type a price into the data yourself.
4. Public claims/FAQs need a non-demo source on phonerepairs.nl (`npm run validate:data` enforces this).
5. Demo-only content is marked with `DemoNote` and disappears with `NEXT_PUBLIC_DEMO_MODE=false`.
6. Changed URLs get a 301 via `src/data/url-inventory.json`. Keep original URLs where practical.
7. The site stays noindex until `NEXT_PUBLIC_ALLOW_INDEXING=true` is set for the approved launch.
8. The appointment form must never claim a booking was sent while no backend is connected.
9. The 3D stand-in phone is not an accurate iPhone 17 teardown and must stay labelled as temporary in demo mode until a licensed model is supplied.

## Conventions
- Dutch UI copy, informal "je". English code and comments.
- Contact priority (client requirement): WhatsApp first, then phone (073 822 0013, same number), e-mail last. Use `ContactActions` for CTA rows, `WhatsAppCard` for in-page prompts and `whatsappHref(whatsappMessage({ device, repair }))` for prefilled links; the floating `WhatsAppWidget` never opens by itself: once per session it shows a bullet on the WhatsApp button (launcher on desktop, bar on mobile; client requests 2026-10-14 and 2026-10-16). The widget copy in `site.whatsapp` is verbatim from the current site.
- House style (client requirement): green `#106f31` (`accent`), grey `#515151` (`muted`), dark `#222222` (`ink`, `night`), typeface Open Sans. The official logo (sent 2026-10-14) is in `public/brand/` and switched on via `site.logo`: `logo.png` / `logo-light.png` are a horizontal arrangement of the original artwork (`logo-original.png`, stacked), cropped, never redrawn.
- Design tokens live in `src/app/globals.css` (`@theme`); use `text-ink`, `text-muted`, `bg-mist`, `text-headline`, etc. — no raw hex in components. The page base is a light grey (`canvas`); cards are `bg-white`. Client request (2026-10-13): darker overall with #222 as main colour and the grey used a lot. Dark and grey bands use the `tone-dark` / `tone-grey` scopes (they redefine the text/line tokens; white cards inside get the light tokens back, other light surfaces inside need `tone-light`). Page headers (`PageIntro`) and the top bar are `tone-dark`; cards use `bg-surface` (white in the light theme, dark grey in the dark theme), `bg-white` only for what must stay white (product photos with `tone-light`, third-party widgets); dark fills use `bg-night`, never `bg-ink`. Dark theme: `<html data-theme>` set before paint by `ThemeScript` (device setting unless the visitor chose via `ThemeToggle` in the top bar, key `pr-theme`), tokens redefined in `globals.css`, `dark:` variant available; use `<Aura>` for soft colour fields and the `glass` / `glass-dark` utilities for frosted surfaces. Green text on tints uses `text-accent-strong`; on dark backgrounds `text-accent-light`.
- Server Components by default; `"use client"` only for interaction (header, finder, form, exploded phone).
- Respect `prefers-reduced-motion`; reveal-on-scroll is CSS (`.reveal`), content is never hidden without JS.
